# /web — project conventions

**Read `../backend/API.md` before adding any API call.** It is the complete request/response
contract — every route, entity shape and error code — written so you never need to read backend
source. **Read `../handled.md` before adding an error path**, and add to it when you add one.
`issues.md` is this project's work queue, including a list of things that are explicitly out of

## Server and client components

Catalog pages are server components (`app/(shop)/page.tsx`, `products/`, `categories/`);
everything behind auth is a client component.

That split is not stylistic. The session JWT lives in `localStorage` (`store/auth-store.ts`), so
the server has no way to read it — an authed page therefore has to render, hydrate, and *then*
fetch. Do not "fix" an authed page by making it a server component; it would have no token. If
that tradeoff is ever revisited, it is one change (session in an httpOnly cookie) that unlocks all
of them at once.

In server components, fetch in parallel and degrade per section rather than per page —
`app/(shop)/page.tsx:14-17` is the reference: each section `.catch(() => null)`s independently so
one dead endpoint does not blank the route.

## One fetch path

**Every** network call goes through `apiFetch` in `lib/api/client.ts`, wrapped by a typed helper
in `lib/api/*.ts`. Never call `fetch` directly from a component.

It gives you three things worth knowing:

- Transport failures (server down, DNS, offline) become `ApiError` with `code: "NETWORK_ERROR"`,
  not an unhandled rejection. `isNetworkError` / `isServerError` are the predicates.
- The backend's Zod error envelope is parsed into `ApiValidationError.fieldErrors`, ready to feed
  back into a `react-hook-form` field.
- Errors always carry the backend's `code` (`NOT_FOUND`, `CONFLICT`, `MANDATE_EXPIRED`, …).
  **Branch on `code`, never on message text.**

Catch specifically. `lib/api/catalog.ts:notFoundToNull` is the pattern: intercept the one code you
can handle, let everything else reach an error boundary.

## Stores

`store/*.ts`, zustand. Rules learned the hard way:

- **A persisted store must set `version` and a `migrate`.** `chat-store.ts` shipped without one,
  and a v2 transcript in `sessionStorage` rehydrated straight into v3 widgets and crashed the
  panel. If you add a required field to anything persisted, bump the version and drop or migrate
  the old shape.
- **Do not persist derived or transient state.** `auth-store` deliberately persists only `user`
  and `token`, not `status` — so the server render and the first client render both start at
  `idle` and the guards show a spinner instead of flashing protected content.
- **Anything user-scoped must be cleared on logout.** `auth-store.logout()` resets the cart store
  for exactly this reason; a store that keeps user data across a logout leaks it to the next
  person to log in on that device.
- Distinguish "the token is invalid" from "the network hiccuped." `hydrateFromServer` clears the
  session on the first and keeps it retryable on the second — a backend restart must not log
  everyone out.

## The chat protocol

`lib/chat/protocol.ts` mirrors `backend/src/chat/protocol.ts`. They are two copies of one wire
format, by design (the projects share no code).

- **`CHAT_PROTOCOL_VERSION` must be bumped on both sides in the same change.** A mismatch is a
  deliberate, loud 400 — better than silently rendering `undefined`.
- That version guards the **request only**. Parts already written to `chat_messages.parts` and to
  `sessionStorage` are replayed as-is, so **treat every new field on a part as optional on the
  client** and degrade rather than throw. A widget that assumes a field exists will crash on old
  history.
- Widgets are projected from tool results by the backend's `partMapper`; the model never authors
  them. If a widget needs data, add it to the part type on both sides — a prompt that tells the
  model to "let the widget show the detail" is worthless if the wire type has nowhere to put it.

## UI

shadcn/base-ui components in `components/ui/` — generated, so prefer composing over editing them.
Use `components/common/empty-state.tsx` and `error-state.tsx` rather than writing new
empty/error markup; `sonner` (`toast`) for transient feedback.

Images are plain `<img>` throughout and `next/image` is deliberately not wired up — see the
out-of-scope list in `issues.md` before "improving" this.
